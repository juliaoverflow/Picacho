# Using Picacho

## Run

The ready-to-open macOS application is **`dist/Picacho.app`**.

```sh
open dist/Picacho.app
```

Or run from source:

```sh
cargo run --release --locked
```

With no accounts, Picacho opens a short setup: choose your provider, sign in, and your mail starts syncing. **Add Account** (in the sidebar, Settings, or the File menu) shows the same setup in a dialog.

A fictional sample inbox is available for development and screenshots. It is compiled out by default; enable it with `cargo run --features sample-data` and choose **Explore a sample inbox** on the welcome screen.

## Sign-in and connection security

Browser sign-in finds out which address was chosen from the provider, so the address is never typed.

For another provider, settings discovery follows Thunderbird's order: the domain's autoconfig file, Mozilla's ISPDB, the domain's MX records (which detect Google Workspace and Microsoft 365 custom domains, then use those services' sign-in), and common hostnames such as `imap.<domain>`.

**Organizations' single sign-on.** An IMAP or POP3 account can sign in in the browser with its organization's identity provider (Okta, Microsoft Entra ID, Keycloak, Authentik, ADFS and others that speak OpenID Connect or OAuth 2.0), including ones that sign people in through SAML 2.0 behind it: Picacho only sees their pages in the browser. Where the domain's autoconfig file says its servers take OAuth2 tokens and names the identity provider (Thunderbird's `<oAuth2>`), this is set up by itself. Otherwise turn on **Sign in with your organization** under **Server settings** and enter the sign-in service's address (its issuer URL), and the client id your administrator registered for Picacho where the provider doesn't let apps register themselves (a public client, PKCE, redirect `http://127.0.0.1`). The mail servers have to accept the provider's tokens (OAUTHBEARER or XOAUTH2).

Incoming connections use implicit TLS with certificate and hostname verification. The one exception is Proton Mail Bridge, which only runs on this computer: Picacho upgrades its connection with STARTTLS and still verifies the certificate, so Bridge's certificate must be trusted (Bridge offers to install it on macOS). SMTP requires STARTTLS, or implicit TLS on port 465. Plaintext connections and certificate bypasses are not offered.

Proton Mail can also connect without Bridge: Picacho signs in to Proton's API itself (SRP, so the password never crosses the wire, with the server's SRP modulus checked against Proton's signing key), with an authenticator app's code when two-factor authentication is on and the mailbox password in two-password mode. When Proton asks to check that it's you (its CAPTCHA, or a code by email or text), its page opens in a window of the system's own webview (WKWebView, WebView2 or WebKitGTK); once it passes, the sign-in continues by itself. That window only goes to Proton and the CAPTCHA services it uses, keeps no cookies, and opens other links in the browser. A check asked for outside a sign-in shows as a sign-in problem on the account; signing in again shows the check. Choosing Proton Mail offers two tabs: Direct (this) and Proton Mail Bridge. Direct signs in in steps: the password, then, where the account has them, its second factor and its mailbox password. The second factor is the code from an authenticator app, or a security key or passkey: a USB security key (asked for its PIN if it has one), or a passkey on a phone, by scanning a QR code with the phone's camera, with Bluetooth on on both devices so the phone can show it's nearby. On Windows 10 1903 and later, Windows Hello handles passkeys and security keys itself; on earlier versions Picacho offers them as on other systems. Passkeys kept in macOS's iCloud Keychain or a browser can't be used for Proton by other apps. The password isn't kept: the keychain holds the session and the salted key passphrase that unlocks the account's keys. Messages are decrypted on this computer when they're opened or downloaded for offline reading, and cached as standard MIME, as mail through Bridge is. Sending goes through Proton, which encrypts for the recipients it can and keeps a copy in Sent. It offers what the same account offers through Bridge, using the same Proton APIs Bridge does: drafts sync with Proton's Drafts, new mail is pushed (from Proton's events, every 20–40 seconds), changes made offline wait and reach Proton with the next connection, Mark All Read covers the whole mailbox, and a copy of what an address sends through its own outgoing server is added to Sent. Server search lists the whole mailbox from Proton and matches it here: on what Proton says about each message, and on its contents where they're downloaded (Proton can't search encrypted contents itself; Bridge searches the copies it keeps the same way). Snoozed mail waits in Picacho/Snoozed at Proton. Messages over 200 MB are read without their attachments, which download when saved. Server filters aren't offered, as they aren't through Bridge.

Passwords sign in with the strongest method the server offers. IMAP, POP3 and SMTP use SCRAM-SHA-256 or SCRAM-SHA-1 where offered: the password never crosses the wire, and the server has to prove it knows the password too. Otherwise IMAP uses `LOGIN` and POP3 `USER`/`PASS`, SMTP uses `PLAIN` or `LOGIN`, all inside TLS. CRAM-MD5 is used only where nothing else is offered. Browser sign-in (OAuth) uses OAUTHBEARER where the server offers it, otherwise XOAUTH2.

## Settings

**Settings** (⌘, on macOS, Ctrl+, elsewhere) has a General page for light, dark, or automatic appearance and the theme color, a global **Reading** page for HTML rendering and remote-content defaults, and a page per mailbox for:

- **Keep mail from**: 2 weeks, 1 month, 3 months, 1 year, or all mail. Older mail stays on the server and leaves the local cache at the next sync. (IMAP accounts.)
- **Check for new mail**: every 1, 5, 15, 30, or 60 minutes, or manually.
- **Notifications**: a system notification for new inbox mail while Picacho is in the background.

General's **Background** section:

- **Keep running in the background** (on by default): closing Picacho's last window leaves it running, without the window, checking every mailbox's inbox on its schedule (and with IDLE or Proton's events) and notifying of new mail. Scheduled mail (Send Later) is sent when due, snoozed mail comes back to the inbox, and sent mail nobody replied to in time is recalled (follow-up reminders), each with a notification; a scheduled message that can't be sent stays in Drafts saying why, as with the window open. A tray icon shows meanwhile (in KDE's or the AppIndicator extension's tray on Linux, the notification area on Windows, the menu bar on macOS); its menu opens Picacho again or quits it, as **Quit Picacho** (⌘Q, Ctrl+Q) does from the window. Launching Picacho again, or clicking its Dock icon, opens the window. Turned off, closing the last window quits.
- **Show tray icon while open**: shows the tray icon while a window is open too.
- On Android, **Check for mail in the background** (on by default) keeps checking after Picacho is closed (swiped away from Recents) and after the phone restarts, with an ongoing notification whose **Stop** ends it until Picacho is opened again.
- On iOS, **Check for mail in the background** (on by default) asks iOS to wake Picacho from time to time while it isn't open: each time, it checks each inbox that's checked on a schedule once, announces new mail, sends scheduled mail and brings back snoozed mail. iOS decides how often (by how you use Picacho) and does it only while Background App Refresh is on for Picacho in iOS's Settings; mail isn't pushed the moment it arrives, as it is while Picacho is open.

**Privacy**:

- **Lock Picacho** asks for a passcode (at least 4 characters) when Picacho opens and when it comes back after being away, that is with none of its windows in front (on a phone, in the background), for the chosen time: immediately, or after 1, 5, 15 or 60 minutes. **Unlock with Touch ID / Face ID / Fingerprint or Face** appears on macOS, iOS and Android 10 and later when the device has biometrics set up; the passcode always works too. **Lock Now**, the Picacho menu's **Lock Picacho** and ⌥⌘L (Ctrl+Alt+L) lock at once. While locked, the main window shows only the lock screen and message, composer, Settings and widget windows show a cover; mail is still checked and announced, and the background process and Android's service never ask. After five wrong passcodes each try waits, 30 seconds and then twice as long each time (up to an hour), across restarts. Changing the passcode or turning the lock off needs the current passcode. A forgotten passcode can only be cleared by removing Picacho's data directory. On phones, with the lock on, the screen is covered whenever Picacho leaves the front, so the app switcher's picture shows no mail; Android 13 and later also leave Picacho's picture out of Recents (screenshots still work).
- **Hide mail outside Picacho** keeps senders, subjects and previews out of notifications (they say how many new messages, for which account) and out of widgets, whose snapshot keeps its rows, counts and dates but not who, what, events' names and places, or packages' and receipts' details. Turning on the app lock or encryption turns it on; it can be turned off again.
- **Encrypt the local database** rewrites the mail cache with SQLCipher (AES-256 pages with HMACs, its write-ahead log too) under a random 256-bit key kept in the system keychain (Keychain, Credential Manager, Secret Service, or Android Keystore–protected storage), and turned off rewrites it unencrypted and removes the key. The keychain entry's name (not the key) is kept beside the database in `mail.sqlite3.keychain`. Picacho opens the database without asking, so this protects the files at rest (a copied disk or backup), not a running, unlocked session; use the app lock with it. If the key is lost, the database can't be read. Picacho then opens a window saying so instead of the mail window, with **Try Again** (for a keychain that was locked or refused), **Quit**, and, when the key is gone or wrong, **Start Over**, which moves the database aside as `mail.sqlite3.unreadable-<time>` (with the name of its key beside it; nothing is deleted, and with its key back it could be put back) and starts with an empty one: accounts are added again and mail on their servers downloads again, while local-only drafts and POP mail removed from the server stay in the old file. Widget snapshots (`widget-snapshot.json`, redacted with **Hide mail outside Picacho**), opened-attachment copies, and pages freed before encryption on the disk itself stay outside the encrypted database.

A red warning beside a mailbox (also in the collapsed sidebar) means it needs
attention. Click it, or open that mailbox's settings, for the operation, time,
underlying cause, and recovery actions. Background failures keep cached mail
available and do not create global error toasts or appear in unrelated settings.
Authentication or Keychain failures pause automatic work for that mailbox until
you retry or sign in again. Connection failures follow the normal polling
schedule. Sign in again preserves the mailbox's identity, cached mail, drafts,
and synchronization preferences. Sending errors also stay in the compose form
so the unsent draft can be corrected.

The window adapts down to 360 × 320 logical pixels. At narrow widths, opening a message shows a full reader with Back navigation; settings moves account navigation above the page and wraps synchronization choices. See [DISPLAY.md](DISPLAY.md) for layout rules and checks.

## POP3 behavior

POP3 downloads are identified by stable UIDL values, cached, and deduplicated. Read/star flags and folder moves are local. Refresh preserves these local changes. Originals remain on the server unless Settings → account → **Remove from the server** says otherwise (After download, after a week, after a month; Never by default). Only messages whose whole source is saved here are removed, after the download is committed, and the server removes them only when it confirms the session's end (`QUIT`); a check that ends without that confirmation removes nothing and the next one decides again. Mail deleted permanently here is remembered so it doesn't download again, and with **Delete on the server too** it is removed from the server at the next check. Sent messages are saved locally after SMTP acceptance.

## Implemented interactions

- A sidebar listing every account as a collapsible group with its standard mailboxes and server folders (nested beneath the inbox). It collapses to an icon rail with ⌃⌘S.
- **All Mail** under each account lists every message in the account at once: the inbox, sent, archive, spam, trash and the account's own server folders (drafts aside), newest first, with each message listed once even when it is in several folders (Gmail's labels). Refreshing it checks each of those folders; on Gmail, its own All Mail plus Spam and Trash. Moving a message there keeps it in the list. With more than one account, **All Accounts** (formerly All Mail; Settings → General → Mailboxes) lists every account's mailboxes together at the top of the sidebar, its All Mail included.
- On IMAP accounts, server folders are made and renamed the way the sidebar's own folders are: right-click the inbox for **New Folder**, or one of your own server folders for **Rename…**, **New Folder Inside** and **Delete Folder…**. A new folder appears in place as "New Folder" with its name selected; names are edited in place (double-click a folder to rename it), Enter or clicking away saves, and Escape keeps the name (a new folder is still made). A new folder goes at the end of its folder (or of the list) and stays there, and a renamed one keeps its place, as with top folders; folders made in other apps follow, by name. Changes are made on the server, and the sidebar shows the new name meanwhile; renaming a folder downloads its mail again under the new name. Deleting a server folder asks first, since it deletes the folder's mail on the server.
- Right-click menus for accounts, mailboxes, and messages.
- **Delete Permanently…** for messages in Trash or Spam (one or a selection), and **Empty Trash…**/**Empty Spam…** on those mailboxes; both ask first. Only the named messages are removed (`UID EXPUNGE`); on servers without UIDPLUS, nothing is changed while another app has left messages marked for deletion there.
- **Labels…** in a message's (or a selection's) menu: IMAP keywords, or Gmail's labels. Labels in use are listed, checked where set; **New Label…** adds one. Labels show under the reader's subject, where they can be removed or clicked to find mail with them (`label:`). Keyword servers only take one-word labels, and only where the folder keeps new keywords.
- Multi-select with the list's Select button, ⌘-click, ⇧-click, ⌘A, the avatar checkboxes, or a message's right-click menu (Select, Select All From Sender), with a bulk toolbar for read/unread, star, archive, spam, and trash. While several messages are selected, the reader pane summarizes them and offers the same actions; ⌘⇧U and ⌘⇧S mark or star the whole selection.
- A filter menu for unread, starred, and attachment-bearing mail, plus newest/oldest ordering.
- Star, read, and move changes apply instantly and roll back if the server rejects them.
- Background download of full messages into the local cache, with progress at the bottom of the sidebar (a ring when collapsed).
- Search and unread filtering within the currently loaded mailbox. Every word must match. Search terms: `from:` (sender name or address), `reply-to:`, `to:` (To or Cc), `cc:`, `subject:`, `is:unread`, `is:read`, `is:starred`, `is:unstarred`, `has:attachment`; a leading `-` excludes (`-from:noreply`) and quotes keep spaces (`from:"Ana López"`). A message's right-click menu searches for its sender or its Reply-To address. Reply-To and Cc come with the list headers of mail synced from now on; older cached mail has them once downloaded in full.
- Proton's own aliases (Settings → Forwarding → Add Service → Proton): for a Proton account signed in without Bridge, its hide-my-email aliases (kept in Proton Pass, separate from a SimpleLogin account of your own) are listed and managed without an API key: with the account's own sign-in, or, in builds with a Proton Pass registration, a Pass sign-in of its own when the service is added, in the same steps as signing in to Proton Mail (password, then the account's second factor). They work as SimpleLogin's do, reverse aliases included; descriptions and display names are the alias's own, not its Pass item's, and contacts' counts cover the last 14 days. The account's own addresses, all but its original one (and the one it signs in with here), are listed with the Pass aliases, marked with their kind (Proton address, your domain, premium, external): they can be turned on and off, named, shown on their own and deleted (where Proton allows it), and sent as directly, since Proton sends from them itself; they have no descriptions, pins, mailboxes or reverse aliases. Making the first alias of an account that has never used Pass makes it a vault named Personal. An account that protects Pass with an extra password needs it entered there too (kept in the system keychain). When Proton ends the Pass session, the service's card says so with **Sign In…** (also **Sign In to Proton Pass…** in its menu): a dialog like signing in to a Proton Mail account again, with the password and extra password, then the account's second factor; the new session replaces the old one, which is signed out.
- Send only as aliases (Settings → Forwarding, per service that can send): the mailboxes the service forwards to can't write as themselves. New mail and replies start out as an alias (the one a message came to or went out as, else the first pinned or turned-on alias), the From menu leaves those mailboxes out, and sending without an alias is refused. Wherever the mailbox's address appears in its received and sent mail (headers, details, body, quotes in replies and forwards), the alias used is shown instead. Recipients written to through a SimpleLogin reverse alias (in To and Cc, and in replies and forwards) show as the contact the reverse alias forwards to; From on sent mail still shows the alias. Contacts are learned when sending, when an alias's reverse aliases are listed, and, for older mail, fetched once per alias per session when such a message is opened.
- Local AI (off by default; Settings → Local AI): small models that run on this computer, downloaded only when a feature that needs one is turned on. Turning a feature off deletes its model; turning Local AI off deletes them all. Settings → Local AI lists the models with whether each is installed (a ring shows a download's progress), its size, the features that use it, and a delete button that says which features deleting turns off. Mail never leaves the computer. **Hide sign-in codes** finds two-factor, verification and sign-in codes in received mail in 37 languages (codes in ASCII, fullwidth, Arabic-Indic, Devanagari, Bengali or Thai digits) (a pattern finds candidate numbers, and a 1 MB model decides from the words around each; Core ML runs it on macOS) and shows them as •••••• in subjects, previews, the message (plain text and HTML text; link addresses are left working), message windows and new-mail notifications. A message with a hidden code says so above its text, with **Show Code** (for this session) and **Copy Code** (copies it as typed into a sign-in form — without spaces or a "G-" style prefix — while it stays hidden). Replies and forwards quote the message as it is. See `models/otp/README.md`.
- **Suggest replies** (Settings → Local AI, off by default): the reply suggestion model (about 1.2 MB, `models/replies`) reads received mail and offers up to four short replies under it (and in the Reply menu on phones and tablets), each marked with a sparkle. It picks from 59 replies worded by hand in 37 languages, in the message's language (told from its script and common words; the computer's language, or English, when it can't be told). Choosing one opens a reply where replies open, with its text written in above the signature and quote and the cursor after it; with a reply to the message already open, the text goes at the top of that one. Reply to everyone by default makes them answer everyone. Replies chosen are offered more; right-clicking one offers **Don't Suggest This**; **Forget**, beside the setting, clears what was learned. That history stays on this computer. Nothing is offered where the model finds the message wants no reply, nor for mailing lists, no-reply senders, sign-in codes, receipts, package updates, drafts or sent mail. See `models/replies/README.md`.
- Tracking removed from links in mail (on by default; Settings → Reading → Remove tracking from links), using [url-sanitize](https://github.com/antonio-orionus/url-sanitize) with its merged ClearURLs, Brave and Firefox rules: campaign and click parameters such as `utm_*`, `fbclid` and `gclid` are dropped, and known redirect wrappers open their real address. Opaque click trackers whose destination isn't in the link are left as they are. The rule catalog and its licenses are in `assets/url-sanitize`.
- Native selectable message text, interactive HTML rendered with Blitz, MIME decoding, attachment listing and saving.
- Compose, reply, reply all, forward, and file attachments.
- Formatted messages are written as they will look: bold, italic, underline, strikethrough, code, headings, bulleted and numbered lists (Tab and Shift-Tab nest an item), quotes, links (⌘K/Ctrl+K asks for the address; a selected address links to itself), alignment and Clear formatting, from the toolbar or their shortcuts. Pictures pasted, dropped on the text or carried by pasted HTML show in the text where they go, in the line beside the words around them when they fit, and are sent inline with the message; ones shown in the text aren't listed with the attachments. Click a picture to select it, then drag the grip at its corner to resize it. Tables show as tables, their cells side by side. Words spelled wrong get a wavy underline: right-click one for spellings, **Learn spelling** or **Ignore spelling** (Settings → Composing → Check spelling turns this off). macOS and Windows use their own spellchecker in the languages set in the system; Linux uses the Hunspell dictionaries installed for LibreOffice or Firefox (none installed, nothing is underlined), and words learned are kept with Picacho's data. On phones and tablets the keyboard checks spelling; a long press selects a word, its handles adjust the selection, and the menu offers Cut, Copy, Paste and Select all. Copying gives other apps the formatting, pictures included. ⌘⇧P/Ctrl+Shift+P previews the HTML that is sent. Rich Text off turns the message into plain text; on again with the text unchanged, its formatting comes back.
- Pasting copied rich text (from a browser or word processor) pastes plain text by default; a “Paste with formatting” button just after keeps its formatting (into a plain message, it becomes formatted). Pictures that live on the web are left out of what's pasted, as they could tell the sender who read the message. Settings → Composing → Paste with formatting swaps the default, offering “Paste without formatting” instead. The button goes once you keep typing. On iOS, formatting copied as RTF (Notes, Pages) or a web archive (Safari) works too.
- SMTP delivery; failed sends retain the draft. Where the server offers them, the sender and recipients go in one round trip (`PIPELINING`) and the message goes as is in `BDAT` chunks (`CHUNKING`).
- **Send Later**: the clock beside Send offers later today, tomorrow morning or afternoon, and Monday morning, or a typed time ("14:30", "tomorrow 9:00", "2026-11-20 9:00"). The message waits in Drafts, which shows when it goes. Opening it shows the time with **Don't Send Later**, and it isn't sent while it is open. Scheduled messages go while Picacho is open: one whose time passed while it was closed goes within a minute of opening. If the server can't be reached, Picacho tries again every five minutes. If the server refuses the message, it stays in Drafts with the reason.
- **Other addresses** (Settings → account → Sending): addresses a mailbox also sends as, each with its own name and Reply-To, chosen in From under their mailbox. Each goes through the mailbox's outgoing server, if that server allows sending as the address, or through an outgoing server of its own. Picacho signs in there once to check before saving, and keeps its password in the system keychain. Replies to mail sent to one of these addresses are written from it. Copies of what they send go to the mailbox's Sent folder, including on Gmail and Outlook when the address uses its own server.
- **Require encryption in transit** (Settings → account → Sending, off by default): messages are sent with `REQUIRETLS` (RFC 8689), so every server on the way must use verified TLS or bounce the message rather than pass it on in the clear. The outgoing server has to offer `REQUIRETLS`; if it doesn't, nothing is sent and Picacho says why. Before sending, Picacho checks each recipient's domain for an MTA-STS policy (RFC 8461) or DANE records (TLSA for its mail servers). The "Message sent" notice names any domain that publishes neither, because mail there will bounce.
- Automatic local draft saving and reopening; save on window close and quit. On IMAP accounts drafts sync with the server's Drafts folder: drafts written here are uploaded when a composer closes and with inbox checks (a new version replaces the old), drafts written in other apps appear here with their attachments, and a draft sent or deleted on one side goes from the other. A draft changed here since its last upload is never discarded.
- A Reply-To per message (Reply-To in the composer, beside Cc and Bcc) and per mailbox (Settings → account → Sending), and optional read receipts (Disposition-Notification-To) and delivery receipts (SMTP DSN, where the server offers it) per mailbox.
- A sign-in name for servers that don't use the email address (Settings → account → Sign-in, or when entering server settings by hand), used for IMAP, POP3 and SMTP.
- Storage use and limit for IMAP mailboxes whose server has quotas (Settings → account → Storage).
- Server read/star flags and atomic IMAP moves where the server supports `MOVE`; elsewhere, a copy and removal of just the moved messages (`UID EXPUNGE`).
- New inbox mail shows as it arrives on servers with IMAP `IDLE`; scheduled checks continue as before.
- Light, dark, and automatic appearance with seven theme colors; tooltips, keyboard shortcuts, and animated reader/dialog entrances.
- A full macOS menu bar: the Picacho menu (About, Settings ⌘,, Services, Hide, Quit), File, Edit, View, Mailbox (⌘1–⌘8, ⌘8 being All Mail), Message, Window, and Help. Shortcuts use Ctrl in place of ⌘ on Windows and Linux.
- Per-mailbox refresh schedules and new-mail notifications.
- **Export as Mbox…** and **Import Messages…** in a mailbox's right-click menu. Exports write every cached message of the mailbox (downloading those only known by their headers), oldest first, to one mboxrd file; Pinal Mail's are decrypted first, so the file opens anywhere. A message that can't be read (not available offline) is left out and counted in the notice. Imports take `.mbox` files (mboxrd or mboxo) and single `.eml` or Outlook `.msg` messages, up to 40 MB each, and add them read: with IMAP APPEND, JMAP Email/import, Proton's import, or, for POP3, to this computer. Starred, All Mail and Drafts take no imports.
- **Contacts** (Settings → Contacts): a CardDAV server's address books, found from the server's address (its `/.well-known/carddav`, the user's principal and its address book home; HTTPS only, same-host redirects only), read at startup and with **Read Now**. **New Contact** and clicking a contact edit its name, email addresses, phone numbers, organization and note. With a server, changes go there (new contacts to the first address book you may write to) with `If-Match`/`If-None-Match`, so a contact changed elsewhere meanwhile isn't overwritten; everything else on the card (photos, addresses, birthdays) is kept as it was. Without one, contacts stay on this computer. vCard files (3.0 and 4.0) can be imported and exported. The CardDAV password is kept in the system keychain. **Disconnect** forgets the server's contacts and password. Address-book people are suggested before people from mail.
- **Calendar** (Settings → Calendar): invitations in mail (`text/calendar` parts and `.ics` attachments; iCalendar's REQUEST, CANCEL, REPLY and PUBLISH) show a card above the message with what, when (in your time zone; Olson and Windows zone names are understood), where, the organizer and guests. Where one of your addresses was invited, **Accept**, **Maybe** and **Decline** send the organizer an iMIP REPLY (RFC 6047) from that address, through the account's own way of sending, and the card remembers your answer. A CalDAV server's calendars (RFC 4791) are read a month back and a year ahead at startup and with **Read Now**; accepted invitations are saved to the calendar new events go to (chosen in Settings when there are several), declined ones removed, and cancelled ones removed with **Remove from Calendar**. Settings → Calendar lists what's coming up, a repeating event once for each time it happens: all of RFC 5545's RRULE (BYSETPOS such as "the last weekday", BYWEEKNO, BYYEARDAY, BYHOUR and the rest, by the `rrule` crate), RDATE extra times, EXDATE and changed or cancelled occurrences; repeats keep their local time across daylight saving changes. Times are shown in your time zone, and in the event's own when it keeps another time ("10:00 – 11:00 (18:00 – 19:00 in Asia/Tokyo)"). **New Event** and clicking an event add, edit and delete events: title, start and end (`2026-11-24 10:00`, a date for all day, or with Settings → Local AI → Understand dates, words like "tomorrow at 10" or "every monday at 9", which also make it repeat), an empty end for an hour, the time zone they're in (prefilled with the event's or yours; IANA names or a city, such as "Tokyo"; the editor says what time that is here), place, notes, how it repeats, and guests. A repeat opened from the list is changed or deleted on its own (**Only this one**: a RECURRENCE-ID, or an EXDATE) or with every repeat. Guests are sent an iMIP invitation (METHOD:REQUEST) from the account the event is organized from when it's saved, and a cancellation when it's deleted. Their answers come back as REPLY messages: **Note Their Answer** puts it on the calendar's copy, and only from the guest's own address. A guest proposing another time (COUNTER) shows the time proposed and the current one, with **Move the Event** (it moves, the guest is marked as accepting, and every guest is sent the new time) and **Keep the Time** (DECLINECOUNTER). As a guest, **Propose a New Time…** under an invitation sends the organizer a COUNTER with an optional note. An updated invitation for an event already in your calendar says what changed and offers **Update My Calendar**, keeping your answer. New events are kept in this computer's time zone, as the system names it (`TZ` first).
- **OpenPGP and S/MIME** (Settings → Encryption):
  - OpenPGP keys are imported from armored files. A protected secret key needs its passphrase once, and is then kept unprotected in the system keychain.
  - Keys are found automatically: **Find Key** looks an address up on its domain (WKD, advanced then direct), and on keys.openpgp.org (never on HKP keyservers such as keyserver.ubuntu.com, which list keys under any address without checking it), as Picacho also does before sending encrypted mail to someone without a key. A key in a received message's Autocrypt header is kept for its sender. Found keys are marked as such; a key you imported never gets replaced. Signed mail you send carries an Autocrypt header with your key.
  - S/MIME: your certificate and key are imported from a PKCS#12 file (`.p12`, `.pfx`) with its password. Others' certificates come from the signed mail they send you (kept automatically), or are imported (`.pem`, `.crt`, `.cer`). Signatures are checked against the system's trusted certificate authorities. One that checks out with a certificate they don't vouch for says so.
  - Reading: PGP/MIME (`multipart/encrypted`, `multipart/signed`) and S/MIME (`application/pkcs7-mime` enveloped or signed data, `multipart/signed` with `pkcs7-signature`) mail is decrypted with your keys, its readable content held in memory only, as Pinal Mail's is. Inline PGP (a plain-text body that is cleartext-signed or an armored message) is read too; its attachments are kept beside the text, and encrypted ones (`.pgp`, `.gpg`, armored `.asc`) are decrypted and shown under their own names. The message's details say who signed it, or that the signature doesn't match. A protected subject (protected headers) replaces the "..." shown outside.
  - Sending: the composer's **Sign** and **Encrypt** buttons, shown once you have a key or certificate. With both kinds, a button switches between OpenPGP and S/MIME. Encrypted mail goes to each recipient (Bcc included) and to you, so Sent stays readable here; sending stops and says which addresses have no key. With OpenPGP, **Encrypt the subject too** moves the subject inside the encryption (others see "..."); other headers stay readable. For people whose apps read only inline PGP, the **inline PGP** button (shown with OpenPGP once Sign or Encrypt is on) sends it that way instead of PGP/MIME: the text cleartext-signed, or replaced by an armored encrypted message (signed inside when Sign is on), and each attachment encrypted on its own as `name.pgp`, or, signed only, sent as it is with a detached signature `name.sig`. Inline PGP protects no headers, so the subject stays readable, and is for plain text only: sending a formatted message that way stops and says so.
  - Drafts marked Encrypt are uploaded to the server's Drafts sealed to your own key: OpenPGP drafts to your OpenPGP key (the subject hidden too when chosen), S/MIME drafts to your certificate. They open on other devices with the same key or certificate. Drafts without a key or certificate of yours to seal them with stay on this device.

## Performance and storage

`uniform_list` draws only visible message rows. Filtering runs on preloaded summaries. DNS, TLS, authentication, sync, MIME parsing, downloads, and delivery run on GPUI's background executor. Per-account serialization prevents concurrent network requests from overwriting each other's state while keeping rendering and input responsive.

IMAP lists every message in a mailbox from its first check: rows on screen are listed first, and the rest of the headers arrive in the background, 200 at a time, newest first, with no **Load more** step (see [SYNCHRONIZATION.md](SYNCHRONIZATION.md#catalog-and-placeholder-rows)). Full MIME messages then download in the background in small batches (so other operations on the account are not blocked), newest first. Opening a message that is not downloaded yet fetches it immediately. SQLite uses WAL mode and a mailbox/date index. Credentials and OAuth tokens are stored in the system keychain, not SQLite. The local message cache and drafts are SQLite data in a directory restricted to the current user, unencrypted unless Settings → Privacy → **Encrypt the local database** is on (SQLCipher; see Settings above).

Data lives in the platform directory selected by `directories::ProjectDirs` for `tech.pinal.picacho` (on macOS, `~/Library/Application Support/tech.pinal.picacho`); data from earlier builds is moved there on first launch. For development or isolated tests, set `PICACHO_DATA_DIR` to another directory. Account removal clears that account's local cache, drafts, and Keychain entry; it leaves server mail intact.

## Current boundaries

- POP3 drafts stay on this device. IMAP drafts sync as described above; drafts written elsewhere open with their text, recipients, attachments and HTML formatting: fonts, colors, alignment, tables and the other app's styles are kept and sent as they were, and its pictures by Content-ID show in the text. Scripts, forms and frames are left out. Table columns share the width equally while editing (spans kept); the message keeps the table's own widths.
- Search filters the listed mail as you type; press Return (or **Search the Server** below the field) to search the whole mailbox on the server: Gmail in its own search syntax (X-GM-RAW), other IMAP servers with SEARCH (SORT orders results where offered). The newest 200 matches are listed. Starred refresh searches the standard inbox/sent/archive/spam/trash mailboxes; Gmail uses its All Mail mailbox. Other server folders are listed under each account's inbox; messages can be moved between the standard mailboxes and, on IMAP accounts, into the account's own folders with **Move to Folder…** (in a message's or a selection's menu, the selection summary, and a subscription's **Move All to Folder…**).
- HTML email uses Blitz for CSS layouts, links, text selection, and disclosures. **HTML on/off** and **Remote blocked/allowed** controls above each message are saved per email. HTML is on and remote content is blocked by default; Settings → Reading changes the defaults for all accounts. Remote images, CSS and fonts only load when allowed. Scripts, forms, embedded frames and filesystem resources are disabled. Images the HTML shows from the message's own parts (`cid:`) are displayed, also with remote content blocked.
- **Forward** carries the original's attachments; **Forward as Attachment** attaches the message itself (message/rfc822). Messages up to 200 MB download on opening, in 8 MB pieces that resume after an interruption (background downloads stay at 25 MB); larger ones show their text, read part by part (BODYSTRUCTURE, BINARY where offered), and each attachment downloads when saved. Outgoing messages are limited to the SMTP server's advertised `SIZE` (25 MB where it doesn't say), checked before anything is sent; attachments go with their type (image/png, application/pdf…).
- IMAP moves use `MOVE` where offered; otherwise a copy and `UID EXPUNGE` of just those messages, or, without UIDPLUS, a plain `EXPUNGE` only when no other message there is marked deleted. The app never expunges unrelated messages.
- **Use the Gmail API** and **Use Microsoft Graph**, chosen when adding a Gmail or Outlook account (before the browser): the account reaches its mailbox through the provider's own API instead of IMAP and SMTP, and never connects over IMAP. For Microsoft 365 organizations that turn IMAP off it is the only way in. Mail is listed, read (as MIME), flagged, labeled, moved, searched (with the provider's own search), deleted and sent through the API; drafts stay in step with the server's, offline changes are sent once back online, and snoozed mail waits in Picacho/Snoozed (a label at Gmail). At Gmail, a message is one row in the mailbox its labels put it in (Inbox, Trash, Spam or Drafts; else under the first of your labels, which act as folders; else Sent; else Archive), your other labels are its labels, and changes made elsewhere are read from Gmail's history. At Microsoft, folders nest as in Outlook, categories are labels, Flagged is Starred, and replied and forwarded show as Outlook marks them. Settings → account → Filters edits Gmail's filters or Outlook's inbox rules (one test and one action each; those set elsewhere with more are kept as they are and counted) and the away reply. With Microsoft Graph, Calendar and Contacts in Settings offer the account: Exchange's calendars (a repeating event is one series with its rule, its occurrences changed on their own and those cancelled; changing or deleting one occurrence changes just that one at Exchange; Exchange sends invitations itself, and invitations answered from mail are answered in the calendar too), its contacts, and the people search (**Search the Server** in Contacts), which for work and school accounts covers the organization's directory. New mail is noticed within half a minute: neither provider's push reaches a desktop app, so Picacho asks whether the mailbox changed (one small request). With **Let the server send scheduled messages**, Exchange holds scheduled mail and sends it at its time with Picacho closed (deferred delivery); Gmail's API has no such thing. Imported mail and copies of mail sent as another address through its own server arrive at Microsoft as mail, made from their parts (signed or encrypted mail keeps its form only as MIME, which Microsoft keeps as a draft). Sending through Microsoft takes messages up to 4 MB in one request; larger ones go as a draft whose files upload in pieces. Signed or encrypted mail that large goes as inline PGP (each file protected on its own) where it is plain text with OpenPGP, and is otherwise refused, saying so. Not available through the APIs: the server's quota, and sharing folders (ACL). **Use the Gmail API** / **Use Microsoft Graph** in an existing account's Settings switches it either way: it signs in again in the browser and reads the account's mail again; drafts are kept.
- **Exchange Server** (in the setup's list): an organization's own Exchange (2010 SP2 and later) through Exchange Web Services, for those whose IMAP is off or who want their Exchange calendars and contacts. Sign in with the address and password (and the sign-in name, `DOMAIN\name`, where it isn't the address), with Kerberos, or, where the organization set up hybrid modern authentication, with **Sign in with your organization**: Microsoft Entra signs you in in the browser (its sign-in service is `https://login.microsoftonline.com/<tenant>/v2.0`; enter the Exchange server too, as the sign-in is for it); Picacho signs in with NTLMv2 (never the older, crackable answers), or Basic over TLS where that is all the server takes. The server is found by Autodiscover from the address, or typed (a server name, or the whole `https://…/EWS/Exchange.asmx`). Everything the Gmail API and Microsoft Graph accounts do works here too: mail, folders, categories as labels, flags, replied and forwarded marks, search (Exchange's own), drafts in step, sending (Bcc named for Exchange), scheduled mail held by Exchange, snoozing, undoing moves, imports and sent copies as delivered mail, inbox rules and Out of Office in Settings → Filters, new mail noticed as it arrives (Exchange's streaming notifications; every half minute where those don't get through), the space the mail takes in the account's Settings. Calendar and Contacts in Settings offer the account: Exchange's calendars (read as iCalendar, repeating events with their changed occurrences; Exchange sends invitations itself, and invitations answered from mail are answered in the calendar too), when people are busy (Exchange's availability), its contacts, and the organization's directory for finding people. An item's id changes when it moves at Exchange, so a moved message's row takes its new id. Changing an Exchange event saves it anew (Exchange takes events only as a whole), so guests receive it as an update; the earlier copy goes only once the new one is saved. Servers requiring Extended Protection for Authentication are signed in to, as the sign-in is bound to the TLS connection.
- Gmail/Outlook save their own sent mail, except mail sent as another address through another server. For custom IMAP, and for those addresses, the app appends a sent copy (within the server's `APPENDLIMIT`). If that fails, the "Message sent" notice says so, and the accepted message is not reported as unsent. The copy is kept on this computer and saved with later mail checks (before drafts are synced), oldest first. It isn't saved twice: the Sent folder is first searched for its Message-ID. A copy that is too large for the server isn't kept, and one that still can't be saved after two weeks is dropped. The "Message sent" notice also says when delivery receipts were asked for and the server can't send them.
- Send Later sends while Picacho is open or running in the background (Settings → General → keep running once the windows close: on by default; on Android, the mail service). With Settings → account → Sending → **Let the server send scheduled messages**, servers that can hold a message (SMTP FUTURERELEASE, JMAP HOLDUNTIL) send it at its time even with the computer off.
- Replies and forwards mark their original `\Answered` / `$Forwarded`; moving mail into or out of Spam sets `$Junk` / `$NotJunk` where the server keeps keywords; read receipts can be sent or declined (`$MDNSent`). Changes made offline are queued and sent first with the next connection.
- **Snooze** (message menu, reader, selection) moves mail to a Snoozed folder inside a Picacho folder (made if missing; on Proton Mail Bridge, under Folders/) until a chosen date and time, then back to the inbox, unread. Snoozed mail is shared with Picacho on your other computers on every kind of account (through IMAP METADATA where offered, otherwise the message "Picacho: snoozed messages" in the Picacho folder, as for follow-up reminders): it shows as snoozed there and comes back there at its time, and a message woken or unsnoozed on one is no longer snoozed on the others; snoozed again, the newer time wins. Earlier versions of Picacho on another computer still read the times kept through METADATA. Snooze and Send Later share a calendar and time picker.
- **Remind me if no reply** (the composer's hourglass, before sending; or **Remind Me If No Reply…** in a sent message's menu and the reader's hourglass in Sent) waits on a reply to the message: in a day, 2 or 3 days, a week or two weeks after it goes (a scheduled message counts from when it goes), or at a chosen time. If nobody replies by then, Picacho reminds you once (a notice, or a notification while the window isn't in front or Picacho runs in the background), and the message's banner offers **Follow Up** (Reply All to your own message, which answers its recipients), **Remind Me Again** and **Stop Waiting**. A reply ends the wait by itself, before or after the reminder: a message of the account naming yours in References or In-Reply-To, or in the same server conversation (Gmail, Microsoft, JMAP, OBJECTID's thread ids), not sent from one of the account's addresses, and not an automatic reply or delivery report (told by its Auto-Submitted, X-Autoreply, X-Autorespond or Precedence header where read, else by its sender or a subject such as "Automatic reply", "Abwesenheitsnotiz" or "Réponse automatique"). Replies are found among downloaded mail as it comes in; before reminding, the server is asked too (an IMAP server searches its inbox and archive; Gmail, Microsoft and Exchange list the conversation; a JMAP server finds the mail naming yours; Proton's conversation is read from All Mail), so a reply not downloaded yet, or filed elsewhere by a rule, still counts. When the server can't be asked (the account busy, or offline), the reminder waits for it, up to half an hour. Exchange's out-of-office replies and reports are told by their message class, Proton's by its automatic flag. A message sent through Gmail's, Microsoft's or Exchange's API that the service files under another Message-ID is matched to its copy in Sent (same subject, sent at the same moment). **Waiting For** shows under an account (and All Accounts) while it waits on something, with how many are overdue; it lists that sent mail, newest first, an hourglass marking each (red once overdue). What's waited on is shared with Picacho on your other computers: waits set or stopped on one are set or stopped on the others, and a reminder given on one isn't given again on another. Where the IMAP server offers METADATA it is a private annotation on the inbox; everywhere else (Gmail and Microsoft APIs, Exchange, JMAP, Proton, IMAP without METADATA) it is a read message titled "Picacho: follow-up reminders" in a Picacho folder, made the first time there is something to keep and replaced as the list changes. Deleting that message makes your other computers forget the reminders not yet shared again. An account waiting on nothing is looked at once a day, only to notice another computer starting to.
- Server filters and vacation replies (ManageSieve, port 4190, STARTTLS) are in Settings → account → Filters & vacation, for IMAP servers that offer it, and for JMAP servers with JMAP for Sieve Scripts.
- JMAP servers (Fastmail, Stalwart, Cyrus, Apache James…): Fastmail is in the service list, and signs in in the browser (in builds with Picacho's Fastmail registration) or with an API token. For others, **Use another provider** finds the JMAP server from the address where the domain publishes an `_jmap._tcp` SRV record or answers at `/.well-known/jmap`. Otherwise, **Server settings** → **JMAP** takes the server by hand. **Sign in with the browser instead** uses the server's own sign-in page where the server allows apps to register. Reading, sending, drafts, folders, labels (keywords), server search, snooze, quota, filters and vacation replies (JMAP for Sieve Scripts, where offered) and push all go through that one server.
- New mail is pushed with IMAP `IDLE` (one extra connection per account, renewed every nine minutes; with NOTIFY it covers every mailbox, otherwise the open folder gets an IDLE connection of its own) and also found by polling on each mailbox's schedule, while Picacho is open or running in the background once its windows close (a small process with a tray icon on desktops, a foreground service on Android). POP3 has no push.
- OpenPGP keys found automatically aren't verified by anyone: they are whatever the domain, keyserver or sender's mail offered. They're marked "not checked" in Settings → Encryption until you check them: **Check…** shows the key's fingerprint, grouped to read out and as an `OPENPGP4FPR:` QR code, and **Compare** takes the fingerprint its owner gave you (pasted from anywhere; the whole 40 characters must match, spaces, colons and case aside), marking it checked when it matches and warning when it doesn't. **They Match** marks it after comparing in person. Your own key's **Show** displays yours the same way, for others to check. The "Message sent" notice names the recipients encrypted to with unchecked keys. Protected headers cover the subject, In-Reply-To, References, Reply-To and Keywords; From, To, Cc and Date stay outside, since delivery needs them.
- Calendar: tasks from CalDAV servers (VTODO) and JMAP servers (JMAP for Task Lists; lists that are hidden or not subscribed to aren't shown) are listed in Settings → Calendar, and can be added (with a due date or none), edited, marked done and deleted. A repeating JMAP task shows the occurrence to do; marking it done completes that occurrence and shows the next. Tasks' reminders (CalDAV VALARMs, JMAP alerts) are shown with the calendar's. Rules made elsewhere with complex RRULE clauses are expanded and kept as they were; the editor's repeat choices cover daily, weekly, monthly, yearly, and custom rules across all four frequencies (intervals, weekdays, months, days of month, Nth weekday/weekday/weekend day, and ends). Moving an event to a guest's proposed time sends every guest the new time, and they answer again.
- Several calendar and contacts sources at once: Settings → Calendar → **More Calendars** and Settings → Contacts → **More Address Books** add another account's calendars or contacts beside the first (a mail account's provider — JMAP, Microsoft Graph, Exchange, Google through its Calendar and People APIs, Proton without Bridge — or another CalDAV/CardDAV server), each with **Read Now** and **Remove**. Everything shows together; **New events go to** picks any source's calendar, and moving an event to another account's calendar moves it there. **Subscribe** adds a read-only calendar feed (`webcal://` or an `.ics` address) read again hourly, every 6 hours, daily or weekly. Proton calendars take events without guests; events with guests are made in Proton Calendar.
- The app is verified on macOS. The code builds for Windows (with OpenSSL built in), Linux and Android (`sh scripts/build-android.sh` finds Android Studio's SDK and newest NDK when `ANDROID_HOME`/`ANDROID_NDK_HOME` aren't set). Windows has an unsigned per-user installer (`scripts\bundle-windows.ps1`); its unit tests pass under Wine, but the app hasn't been tried on Windows itself, and there are no Windows builds in CI or releases until they can be signed. S/MIME drafts sync sealed to your own certificate, as OpenPGP drafts are to your key.

## Verification

```sh
cargo fmt --check
cargo clippy --all-targets --locked -- -D warnings
cargo test --locked
```

The integration tests use local loopback servers and freshly generated, properly verified TLS certificates. They require `openssl` (included with the macOS developer environment) and permission to open local sockets. They do not contact live providers or send email to external recipients. `cargo test -- --ignored live` runs an opt-in discovery check against public autoconfig servers.

The tests cover IMAP sync/read/flags/atomic moves/cache reconciliation, SMTP STARTTLS authentication and MIME attachment delivery, POP3 TLS downloading and deduplication/local-folder preservation, MIME decoding, POP3 dot unstuffing and command validation, cache/account isolation, local drafts, PKCE generation, autoconfig/MX parsing, and headless UI tests of onboarding, settings discovery, and the account menu. OAuth against live Gmail and Microsoft accounts requires a user to sign in with their own application registration; it cannot be validated without that setup.

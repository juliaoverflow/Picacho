# Developing Picacho

Picacho has three units. `main.rs` only opens the data directory and starts the app.

| Unit | Responsibility | Entry points |
| --- | --- | --- |
| **Sync** (`src/sync/`) | Provider APIs, discovery, OAuth, verified TLS, IMAP/POP3/SMTP and JMAP exchanges, MIME decoding | `imap`, `pop`, `smtp`, `jmap`, `discover`, `oauth` |
| **Manage** (`src/manage/`) | Account operations, per-account serialization, cache reconciliation, SQLite, local drafts, encryption and readable in-memory messages | `Backend`, `Store`, domain types in `model` |
| **Display** (`src/display/`) | GPUI events and views, settings, message reader, assets and notifications | `run`, `ui`, `settings`, `reader` |
| **Display, mobile** (`src/display-mobile/`) | The phone and tablet presentation of the same `MailApp` state: navigation stack, bottom bars, sheets, swipes, safe area and keyboard | `mobile_root`, `Mobile` |

Display invokes Manage on GPUI's background executor. Manage coordinates Sync and persists completed results. Sync's protocol helpers have no database or UI access. Domain types are shared from Manage. OAuth currently saves refreshed credentials through Manage's keychain helper; credentials never enter SQLite. The internal `transport` facade keeps the coordinator's imports small, while protocol implementations remain in separate files.

## Where to make changes

- New provider: start with Sync discovery/OAuth and Manage's `Service`/`Account`. Keep server-specific behavior out of views.
- Incoming protocol: change Sync's `imap.rs` or `pop.rs`; update the coordinator in `manage/backend.rs` for persistence policy.
- JMAP (RFC 8620/8621): the HTTP/JSON client is `sync/jmap.rs`; `manage/jmap.rs` is what each account operation does for a JMAP account, dispatched from `manage/backend.rs` the way Proton's API is. See [SYNCHRONIZATION.md](SYNCHRONIZATION.md#jmap).
- IMAP extensions and the session stream (COMPRESS, IDLE waits): `sync/imap.rs` and `sync/stream.rs`; Manage's `connection.rs` caches capabilities, namespace and rights per connection. Push for new mail lives in `manage/watch.rs`; draft sync in `Backend::sync_drafts`. See [SYNCHRONIZATION.md](SYNCHRONIZATION.md).
- Running without a window: `manage/background.rs` is the monitor that checks inboxes, sends scheduled mail and wakes snoozes, and announces each once the window is gone (desktop and Android alike). On desktops the background is a process of its own, so none of the window's memory stays: as the last window closes, the window's process quits and starts `picacho --background <data dir>` (`display/resident.rs`), which runs only the store, the backend, the monitor and the tray icon (`display/tray.rs`) without GPUI. Opening Picacho hands back: the background process lets the monitor finish (a scheduled send in full), frees the socket and starts the window's process (`--data-dir <data dir>`), so only one of the two ever runs. In a Flatpak each is started through `flatpak-spawn`, outside the sandbox of the process ending. `display/shell.rs` owns what outlives a window in the window's process (the shared `Backend`, the tray icon when Settings shows it with a window open), and `display/instance.rs` hands later launches to whichever process runs. `manage/memory.rs` caps glibc's allocator arenas on Linux and returns freed memory to the system after each background check. On Android, `src/android.rs` and the Java in `android/app/src/main/java` run the foreground `MailService` that keeps the process alive; see the comments there for how the activity, the service and process restarts fit together.
- Database/cache: change `manage/store.rs`. Existing profiles open without a migration or data-directory rename in this reorganization.
- Encryption: change `manage/crypto.rs`; plaintext from encrypted mail must stay in memory.
- HTML renderer: `display/html/` is a reusable component with no mailbox, database, or MailApp dependencies. `document.rs` owns Blitz layout and vector painting, `view.rs` adapts GPUI input and visible-tile painting, and `resources.rs` is the only resource-loading boundary. The reader supplies HTML and a per-email remote-content policy. Reading defaults live in `manage/reading.rs`; both defaults and overrides use Store preferences. See [Picacho-Patches](https://github.com/pinaltech/Picacho-Patches/tree/HEAD/stylo_derive) for the scoped upstream compatibility patch.
- Settings or reader layout: use `display/settings.rs` or `display/reader.rs`. Shared view state and event handling live in `display/ui.rs`.
- Phones and tablets: `src/display-mobile/` is a child module of `display::ui` (declared there with `#[path]`), so it renders the same state and dispatches the same `Action`s, reusing the desktop's message body, Settings pages, setup flow, composer and dialogs inside touch chrome. It is on for iOS and Android builds unless Settings → General → Desktop layout is on, which shows the desktop window instead (`display-mobile/touch_desktop.rs` keeps it in the safe area, above the keyboard and answering Back). `mobile.on` means the phone layout is shown; `mobile.touch` means a touch device with one window, whichever layout it shows. Size desktop controls with `self.tap(desktop, touch)` so they take a fingertip there (code without a `MailApp` reads `window::touch()`), and give anything only dragged with a pointer another way in, as the sidebar's Move Up and Move Down; GPUI turns taps into clicks, pans into scroll events and long presses into right clicks (`touch_desktop`), but a pointer's drag never starts from a finger: `mail_drag` carries messages to mailboxes after a long press instead. Two-finger pinches come from gpui-mobile's `PinchRecognizer` (Picacho-Patches, patch 0003) as `PinchEvent`s; the email view zooms with them (`HtmlView::pinch`). On a desktop, `PICACHO_MOBILE=1` previews it in a phone-sized window (`PICACHO_MOBILE_TOP` and `PICACHO_MOBILE_BOTTOM` set the simulated safe area). Controls are at least `mobile::TOUCH` points; give new text fields a keyboard layout in `keyboard_fields`.

## Verification and commits

Run `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings`, `cargo test --locked`, and `cargo build --locked` before committing a phase. Also test `--features sample-data` when changing onboarding or views. Protocol tests run production code over loopback TLS with test-only trust roots. They need OpenSSL and local sockets, but no real accounts.

On Linux, GPUI needs the development libraries for ALSA, X11/XCB, XKB, Wayland, fontconfig, FreeType, Vulkan, EGL, OpenSSL, DBus and Secret Service, and WebKitGTK 4.1 (with GTK 3) for Proton's verification window (`display/verify.rs`), which runs as a second Picacho process started with `--proton-verify`. Headless view tests use GPUI's test platform. The lockfile keeps `command-fds` 0.3.1 and `libc` 0.2.183 because GPUI's transitive `xattr` 0.2.3 still refers to Linux's removed `ENOATTR` alias; revisit this compatibility constraint when upgrading GPUI.
